# 开发说明

原生 HTML / CSS / JavaScript modules，无运行依赖。生产构建按内容为资源生成文件名，同步更新模块和 Worker 引用；`asset-manifest.json` 用于核对产物。

## 硬件信息的边界

`adaptive-policy.js` 使用浏览器提供的逻辑处理器数量、可选的近似内存档位，GPU 开启后再查询实际 WebGL 渲染器和纹理限制。浏览器可能少报核心数，不一定提供内存或精确显卡型号；网页不能读取机身温度、整机 CPU / GPU 利用率或完整硬件清单。

信息仅用于本页调度，不持久化、不上传。未知核心数在手机/触屏平板按 2、桌面按 4 处理，调度上限为 64 线程；报告内存不超过 1GiB 时上限为 4 线程，不超过 2GiB 时上限为 8 线程。

## CPU：校准、渐进升载、按响应降载

| 档位 | 目标线程数 | 每线程目标工作比例 |
| --- | --- | --- |
| 轻柔 | 可用逻辑处理器的 25%，向上取整 | 40% |
| 温暖 | 可用逻辑处理器的 65%，向上取整 | 82% |
| 热烈 | 可用逻辑处理器全部 | 85% |

例如浏览器报告 8 核且没有低内存限制时，目标分别为 2、6、8 线程。表中的工作比例是调度目标，不是整机利用率。

首次主动开始后，在一个 Worker 内用同一算术内核进行 14 个约 6ms 的短切片：前 2 片预热 JIT，后 12 片测量迭代速度。按每批约 0.35ms 选择 128–8192 次迭代的检查间隔。每个工作切片约 6ms，使用 MessageChannel 让出事件循环，不在主线程忙等。

桌面温暖和热烈从目标线程数减一、最高 75% 工作比例开始；手机/触屏平板从 1–2 个线程起步，同样逐步升至当前档位目标。每 750ms 检查一次：

- 连续两个窗口主线程延迟低于 30ms、Worker 平均周期超时低于 90ms：增加一个线程、工作比例增加 8 个百分点，直到目标。
- 连续两个窗口主线程延迟超过 80ms，或 Worker 平均周期超时超过 180ms：减少一个线程、工作比例减少 12 个百分点。
- 单次抖动不直接降载；中间状态保持。切换档位立即应用新上限并保留截止时间。

Worker 计时反映其自身工作时间和调度延迟，不是操作系统 CPU 计数器。调度器用于尽量增加本页负载并保持响应，不能识别所有温度、系统功耗或其他应用的性能状态。

## GPU：优先硬件计时

优先在独立 module Worker 内创建 OffscreenCanvas + WebGL2；接口缺失、module Worker 失败或后台上下文不可用时，自动尝试 HTMLCanvasElement + WebGL2。两条路径复用 `gpu-engine.js`，页面路径使用小批次、非阻塞 fence 轮询，不在主线程执行 CPU 忙循环。优先请求高性能 GPU。片段着色器执行数学计算，结果在两张 RGBA8 纹理之间交替读写。始终只有一个 GPU 批次在途，使用 fence 非阻塞等待，避免命令积压。

支持 `EXT_disjoint_timer_query_webgl2` 时记录 GPU 命令的实际耗时，丢弃 disjoint / 无效样本；不支持时回退到完成等待时间，并明确标记测量方式。GPU 时间和等待时间分开，不冒充整机 GPU 利用率。

| 档位 | 调度目标 | 初始迭代次数 | 目标单批 GPU 时间 | 分辨率上限 |
| --- | --- | --- | --- | --- |
| 轻柔 | 30% | 96 | 8ms | 768² |
| 温暖 | 60% | 192 | 18ms | 1536² |
| 热烈 | 85% | 384 | 35ms | 2048² |

桌面后台路径从 512² 开始；手机从 128²、最多 96 次迭代开始，先完成小批次再逐步扩展。手机最初 3 批及之后每 6 个完成批次根据完成耗时调整分辨率。页面兼容路径单批目标不超过 8ms，手机后台路径不超过 18ms；这些是反馈目标，不能保证每批一定在预算内完成。达到分辨率上限仍偏轻时增加迭代次数，最多 768 次。取消与画面无关的 60fps 计算限额；高档在一个批次完成后尽快提交下一个。主线程延迟超过 80ms 时降低批次目标和调度强度。

分辨率还受实际 WebGL 限制及内存提示约束，手机与页面兼容模式不超过 1024²，报告内存不超过 2GiB 时不超过 768²；最多两张 2048² RGBA8 工作纹理，约 32MiB，不含驱动开销。

已知软件渲染器（如 SwiftShader、llvmpipe）被拒绝。浏览器未暴露渲染器详情时依赖可用 WebGL 能力，不能保证操作系统选择某块独立显卡。GPU 初次主动开启时才创建上下文；页面初次打开不创建计算 Worker 或 GPU 上下文。GPU 完全不可用时取消选中并禁用该开关，自动选择可用 CPU；CPU 线程失败只关闭 CPU，其他可用路径继续。均不可用时保留炉火、计时和启停，状态直接在 CPU/GPU 行显示，不新增说明面板或故障提示条。用户主动关闭两种设备时只播放炉火。

CPU 池遇到部分线程创建失败时收缩到可用线程数；首个线程不可用时才禁用 CPU。硬件提示用于预算选择，启动成功和实际计算完成用于验证能力，不按 iOS / Android / HarmonyOS 的名称假定支持。手机特征只影响起步和内存预算。

## 可见性与停止

**失去焦点不等于页面隐藏。**网页仍可见时切换到活动监视器继续运行；可以把两个窗口并排查看。切换标签、最小化或被浏览器判定隐藏时立即停止，返回不自动重启。

CPU 与 GPU 每 250ms 接收心跳，独立检查单调时钟截止时间；约 1.4 秒没有心跳会自行退出。离开页面、冻结或到点也停止。系统冻结可能暂停所有执行，恢复后再检查。

CPU 直接终止 Worker。GPU 先请求释放 GL 上下文，最多等 80ms 后终止；已提交的单批可能由驱动完成，不再提交后续批次。最长可选时间 5 分钟，修改定时会重新计时。

## 验证

```sh
npm install --no-save --package-lock=false playwright
npx playwright install chromium webkit
npm run build
npm run preview
# 另一个终端
TEST_GPU_BACKEND=metal npm run verify
TEST_GPU_BACKEND=metal npm run verify:mobile
```

macOS 使用 Metal 验证硬件 GPU；其他环境省略 `TEST_GPU_BACKEND`。`TEST_URL` 可指定站点，`PLAYWRIGHT_MODULE` 可复用已有 Playwright。

策略检查覆盖不同核心数、信息缺失、低内存、升降载及切档边界；浏览器检查覆盖实际 Worker、GPU 硬件计时、停止与界面。整机占用需通过操作系统工具或开发测试的进程 CPU 时间差来测量，普通网页无权直接读取。

## 本轮验收目标

- 核心体验：手机触控与横竖屏可操作；CPU/GPU 缺失或失败不会卡死启动，剩余可用路径继续。
- 硬约束：不自动开始计算，目标工作比例最高 85%（不承诺整机占用上限），隐藏/离开/到期停止，返回不重启，不新增主界面说明，不虚报温度或利用率。
- 技术取舍：没有 WebGL2 时退到 CPU；没有 Worker / MessageChannel 时不使用主线程 CPU 忙循环。CPU/GPU 都不可用时退为炉火展示。
- 可观察条件：手机与横屏主要触控区至少 44px 高且位于屏内；缺少 OffscreenCanvas / module Worker 时页面 GPU 路径实际完成批次；GPU 丢失后 CPU 可继续；停止后线程退出且兼容 canvas 被移除。

自动化手机视口不等于 iPhone、安卓、鸿蒙真机验收；后者尚未完成。无需依据系统名设置白名单，新内核直接按实际接口检测。

## 可观察的运行状态（2.3）

CPU / GPU 开关表示用户选择，运行指示来自计算回报。每次启动、切档或重设定时分配递增 `revision`；Worker 回报 `applied` 确认已接收配置，再由同版本的 `stats` 确认实际产生计算。CPU 新版本会重置统计窗口并重启计算周期；GPU 等在途批次完成后使用新设置，统计保留实际完成批次的版本、档位、尺寸和迭代次数。

CPU 活动线程仅统计最近约 2.2 秒内回报当前版本且有计算的 Worker，吞吐量为各线程的 `iterations / wallMs` 之和。GPU 批次速率来自实际完成计数；GPU 毫秒来自有效硬件查询，缺失时主界面只展示完成速率和计算路径，不把等待时间当成 GPU 耗时。没有任何整机 CPU / GPU 使用率或使用率估算。

状态区区分已停止、已关闭、启动中、应用中、运行中、等待数据、不可用。过期、旧版本、停止或关闭的数据撤下，不沿用旧数字。85% 仅表示最高档目标工作比例，不承诺实际利用率的硬上限。

## 直接播放模拟炉火声

`fire-sound.js` 用 Web Audio 合成滤波粉红噪声、慢速起伏和不规则木柴爆裂；暖炉皮肤降低高频并减少爆裂。不包含外部音频、下载素材或独立声音控件。

电源手势内创建/恢复 AudioContext，计算/视觉成功开始后才连接发声节点。初次打开保持静音且不创建音频上下文。档位与皮肤实时调节音色，手动/到期停止计算后按设备分别播放水声或机械断电声，隐藏/离开/冻结立即断开并挂起；快速重启清理上一段的淡出节点与定时器。音频不可用或被浏览器阻止时不影响其余功能。正常使用仍受系统音量、静音模式和浏览器播放策略影响。

验证入口：`npm run verify:status`，检查真实音频图输出、状态版本确认、过期数据撤下、启停/隐藏释放、快速启停及音频 API 缺失。WebKit/Chromium 手机视口仍不等于手机真机。

## 分设备收尾与档位目标（2.5）

`shutdown.js` 在所有计算已停止后播放 2.7 秒收尾。壁炉使用有立体明暗和火光反射的金属水壶，配合 Canvas 2D 的透明水流、高光水滴、柔边体积蒸汽和多层发光余焰；没有表情脸或描边烟雾。水壶停顿回头后补最后一滴。`shutdown-atmosphere.js` 只在壁炉收尾期间运行 requestAnimationFrame，像素倍率最多 2，取消或结束立即清空画布并停止帧循环。没有字幕、结束提示或说明弹窗。

电暖炉不运行水壶/水滴/蒸汽绘制，也不播放末滴音效。它使用实体旋钮关断、电热丝余温渐暗、单根电热丝短暂回亮、旋钮再次关断；小指示灯与机械开关声同步。两种设备有独立的阶段和动作，没有共用浇水逻辑。

应用 `ending` 阶段的电源是重新点火；启动会取消旧动画、阶段计时器和未来音效，旧回调不能改变新一轮状态。隐藏/离开/冻结与切换皮肤会立即清理动作，减少动态效果时跳过序列。计时结束保留 00:00。停止时 CPU/GPU 数据先清空，不能用熄火视觉代替真实停止。

CPU/GPU 各自的目标值放在状态行标题旁，来自同一份 `MODES`：轻柔 40% / 30%，温暖 82% / 60%，热烈 85% / 85%。GPU 引擎直接读取相同的 `gpuDuty`，避免显示与实际配置脱节。这些是目标工作比例，仍不显示或声称整机使用率。

问号入口、说明 dialog、说明用的数据节点和结束 toast 已从页面移除，使用与运行边界留在 README。验证入口 `npm run verify:ending` 覆盖真实时间三段动作、先停止计算、取消和重启、两种皮肤、隐藏清理、减少动态效果、定时结束、档位目标和 WebKit 手机视口。
